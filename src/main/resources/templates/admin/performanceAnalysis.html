📊 Analisi Sperimentale JPA/Hibernate

Confronto delle strategie di accesso ai dati per il caso d'uso: "Caricamento di tutti i Tornei con le Squadre iscritte". Sezione §8.2 della specifica di progetto.

🎯 Caso d'Uso Analizzato

La relazione tra Torneo e Squadra è @ManyToMany, con una tabella di join iscrizione_squadra_torneo. Il caso d'uso richiede di caricare tutti i tornei con la rispettiva lista di squadre iscritte — operazione comune nella homepage e nella classifica.

  • Strategia 1 — LAZY: comportamento default JPA, genera il problema N+1
  • Strategia 2 — JOIN FETCH: query JPQL con LEFT JOIN FETCH, 1 sola query
  • Strategia 3 — EntityGraph: annotazione @EntityGraph sul repository, 1 sola query

⚠️ Problema N+1 Query

Con N tornei nel database, Hibernate esegue: 1 query per caricare i tornei + N query (una per ogni torneo) per caricare le squadre = N+1 query totali. Con molti tornei, questo degrada sensibilmente le prestazioni.

📝 Conclusioni e Scelta Implementativa

L'analisi dimostra che la strategia LAZY (default) genera il problema N+1: ad ogni accesso alla collection squadre di un torneo, Hibernate esegue una query SQL separata. Con pochi dati il divario è limitato, ma scala linearmente con il numero di tornei.

Le strategie JOIN FETCH e EntityGraph producono risultati equivalenti (entrambe generano una sola query SQL), con la differenza che:

• JOIN FETCH è più esplicita e controllabile (la query è visibile nel repository).
• EntityGraph è più dichiarativa e disaccoppiata dalla query stessa.

Scelta adottata nel progetto: per il caricamento della lista tornei in homepage (/tornei) è stata adottata la strategia EntityGraph tramite @EntityGraph(attributePaths = {"squadre"}) nel TorneoRepository, che garantisce efficienza mantenendo il codice dichiarativo e leggibile.
